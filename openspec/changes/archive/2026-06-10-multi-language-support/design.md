## 上下文

应用为 Electron + React + Vite 架构。当前所有面向用户的文案均为硬编码简体中文，分布在渲染层（`App.tsx`、`components/*`、`shared/filter.ts` 的清晰度标签）与主进程（窗口 `title`）。主进程当前未设置自定义应用菜单（`autoHideMenuBar: true`）。

要实现「菜单 → 设置面板 → 切换语言，默认系统语言」，存在两个跨进程约束：
1. **原生菜单本地化**：应用菜单由主进程（Electron `Menu`）构建，其文案也需随语言切换；菜单项「设置」需要触发渲染层打开设置面板。
2. **系统语言与持久化**：系统语言只能由主进程 `app.getLocale()` 获取；语言偏好需持久化（跨进程一致、重启沿用）。

因此语言状态需要在主进程与渲染层之间协调一致。

## 目标 / 非目标

**目标：**
- 通过系统菜单「设置」打开设置面板，在面板内切换语言。
- 首次启动默认使用系统语言，不支持时回退英文。
- 语言偏好持久化，重启沿用。
- 渲染层与主进程（菜单、标题）的 UI 文案全部翻译化、切换即时生效。
- i18n 基础设施可扩展，新增语言成本低。

**非目标：**
- 不做运行时从远程加载语言包；语言资源随应用打包。
- 首版内置 5 种语言：简体中文（zh-CN）、英文（en）、日语（ja）、法语（fr）、西班牙语（es）；其它语言留待后续按相同机制添加。
- 不翻译第三方源返回的资源标题等动态数据（仅翻译应用自身 UI 文案）。
- 不实现 RTL 布局（首批语言均为 LTR）。

## 决策

### 决策 1：语言偏好由主进程作为权威来源（single source of truth）
- **选择**：主进程持有当前语言。启动时解析「有效语言 = 已持久化偏好 ?? 映射(系统语言) ?? 'en'」。通过 IPC 暴露 `i18n:get`（返回当前语言与支持列表）与 `i18n:set`（持久化 + 重建菜单 + 广播 `i18n:changed`）。渲染层初始化时读取 `i18n:get`，并订阅 `i18n:changed`。
- **理由**：菜单本地化与系统语言读取都在主进程；让主进程持有可避免双进程状态分叉，菜单与界面始终一致。
- **替代方案**：渲染层用 `localStorage` 独占持有——主进程无法据此本地化原生菜单，且无法在首启读取系统语言。

### 决策 2：持久化到 userData 下的 JSON 配置
- **选择**：将偏好写入 `app.getPath('userData')/settings.json`（如 `{ "language": "en" }`）。读写封装在主进程一个轻量模块中。
- **理由**：无需引入额外依赖，跨平台、随用户配置目录留存；为后续更多设置项预留结构。
- **替代方案**：`electron-store`（便利但增加依赖）；首版用原生 `fs` 足够。

### 决策 3：渲染层 i18n 采用轻量自建 Context（不引入重型库）
- **选择**：实现 `I18nProvider` + `useT()`：基于 React Context，持有当前语言与消息目录，`t(key, params?)` 按 key 取文案并做简单插值（`{name}` 占位）。语言资源以 TypeScript 模块按 key 强类型维护。
- **理由**：仅两种语言、文案量可控；自建方案零额外运行时依赖、bundle 更小、契合「即开即用」，且类型安全（缺漏 key 编译期可发现）。
- **替代方案**：`react-i18next`/`i18next`——功能强大（复数、命名空间、懒加载），但对当前规模偏重；保留后续按需迁移空间。

### 决策 4：共享消息目录，主进程取子集
- **选择**：消息目录置于 `src/shared/i18n/locales/{zh-CN,en,ja,fr,es}.ts`，以 `zh-CN`（或 `en`）为基准定义统一的 key 集合与 `Messages` 类型，其余语言实现同一类型。渲染层使用全部 key；主进程仅取菜单/标题相关 key 做本地化。`src/shared/i18n/index.ts` 暴露 `SUPPORTED_LANGUAGES`、`DEFAULT_LANGUAGE`、`resolveSystemLanguage(locale)`、`getMessages(lang)`。
- **理由**：单一事实来源，避免主/渲染两份文案漂移；新增语言只需加一个 locale 文件并登记。以统一 `Messages` 类型约束 5 个 locale，缺漏 key 编译期即可发现。
- **替代方案**：主、渲染各存一份——易漂移。

### 决策 5：菜单结构与「设置」入口
- **选择**：主进程用 `Menu.buildFromTemplate` 构建应用菜单：
  - macOS：在应用名菜单下加入「设置… / Settings…」（`Cmd+,`，`role` 不用自带 preferences，自定义 click）。
  - Windows/Linux：在「文件 / File」或「应用 / App」菜单下加入「设置… / Settings…」。为保证可访问，这些平台不隐藏菜单栏。
  - 点击「设置」→ `mainWindow.webContents.send('settings:open')`。
- 菜单模板文案取自当前语言消息目录；`i18n:set` 后重建菜单。
- **理由**：符合各平台习惯；渲染层负责面板展示，主进程只负责入口与本地化。
- **替代方案**：单独的设置窗口（`BrowserWindow`）——更重，首版用渲染层内模态面板即可。

### 决策 6：设置面板为渲染层模态组件
- **选择**：新增 `SettingsPanel` 模态，含语言下拉（展示各语言原生名，如「简体中文 / English」）。监听 `settings:open` 打开；选择语言即调用 `api.setLanguage(lang)`，主进程持久化并广播，Provider 更新使全界面即时切换。
- **理由**：复用现有渲染栈与样式；切换走统一的主进程权威路径，菜单与界面同步。

## 风险 / 权衡

- [主/渲染语言状态不同步] → 单一权威源（主进程）+ 广播事件；渲染层不独立持久化。
- [遗漏硬编码文案导致混排] → 用类型化 key 集中管理，逐组件替换并审查；缺 key 编译期可发现。
- [系统语言映射不准确（如 `zh-TW`、`zh-Hant`、`ja-JP`、`fr-FR`、`es-ES`、`es-419`）] → 首版按主语言前缀映射（`zh*`→zh-CN、`ja*`→ja、`fr*`→fr、`es*`→es、其余→en）并集中在 `resolveSystemLanguage`，后续可细化区域变体。
- [新增依赖增加体积] → 采用自建轻量方案，不引入 i18n 重型库与 `electron-store`。
- [菜单栏在 Win/Linux 隐藏导致无法进入设置] → 这些平台保持菜单栏可见或提供 `Cmd/Ctrl+,` 快捷键。

## 迁移计划

纯增量、无存量数据。新增 i18n 基础设施与设置面板，逐步把硬编码文案替换为 `t(key)`。首次启动无持久化偏好时按系统语言初始化。回滚：移除菜单设置项与 Provider 即回到中文硬编码（不影响核心搜索功能）。
