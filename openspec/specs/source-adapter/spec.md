## 需求
### 需求:统一的搜索源适配器接口

系统必须定义一个统一的搜索源适配器（SourceAdapter）接口，使每个磁力/种子源以一致的方式被调用。每个适配器必须暴露 `id`、`displayName`、`search(query, options)`、`buildMagnet(result)` 以及能力声明（是否支持清晰度 / 季 / 集筛选）。系统禁止在 UI 或轮询逻辑中直接耦合任何特定源的字段结构。

#### 场景:调用适配器执行搜索

- **当** 上层逻辑通过适配器接口调用 `search(query, options)`
- **那么** 适配器必须返回归一化结果数组，且不要求调用方了解该源的原始响应结构

#### 场景:适配器声明自身能力

- **当** UI 需要判断某个源是否支持季 / 集 / 清晰度筛选
- **那么** 适配器必须通过能力声明字段返回该信息，UI 据此决定展示哪些筛选控件

### 需求:搜索结果归一化结构

所有适配器返回的结果必须归一化为统一结构：`{ id, source, name, seeders, leechers, sizeBytes, infoHash?, resolution?, raw }`。其中 `raw` 必须保留源的原始数据以便回退处理，`source` 必须标识结果来源。

#### 场景:不同源返回统一结构

- **当** 不同源（如 PirateBay、未来的 1337X）返回各自原始格式的数据
- **那么** 适配器必须将其转换为同一归一化结构，使上层逻辑无需区分来源即可处理

#### 场景:缺失字段的处理

- **当** 某个源未提供 `infoHash` 或 `resolution` 等可选字段
- **那么** 适配器必须将对应字段置为缺省（undefined），且禁止因字段缺失而抛出异常中断整次搜索

### 需求:PirateBay 源的内置实现

系统必须内置一个 PirateBay 适配器，通过 `apibay.org` 的查询接口（`q.php`）按名称搜索种子，并实现归一化与磁力生成。当结果缺失 `info_hash` 时，适配器必须支持通过详情接口（`t.php?id=`）二次获取 `info_hash`。

#### 场景:成功搜索 PirateBay

- **当** 调用 PirateBay 适配器并传入有效的影视名称
- **那么** 适配器必须请求 `apibay.org` 查询接口并返回归一化结果数组

#### 场景:info_hash 缺失时回退获取

- **当** PirateBay 查询结果中某条目缺失有效 `info_hash`（例如为全零值）
- **那么** 适配器必须尝试通过详情接口按 `id` 二次获取 `info_hash`，若仍无法获取则在该条目上标记不可生成磁力

### 需求:可扩展的源注册与选择

系统必须提供一个源注册表（registry），允许新增源仅通过实现适配器接口并注册即可被使用，禁止要求修改 UI 或核心逻辑。UI 必须能够从注册表枚举可用源，并支持选择单一源或聚合多源查询。

#### 场景:注册新源后可被枚举

- **当** 一个新源（如 1337X）实现了适配器接口并注册到 registry
- **那么** UI 必须能从 registry 枚举到该源，无需修改 UI 核心代码

#### 场景:聚合多源查询

- **当** 用户选择以聚合模式查询且存在多个已注册源
- **那么** 系统必须并行调用各源的 `search`，合并归一化结果，并在结果中保留各自的 `source` 标识；任一源失败时不得阻断其他源的结果返回
